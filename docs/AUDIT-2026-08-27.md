Read `## The pattern` first. It explains most of what follows.

## The pattern

**Successive rebuilds registered buttons on the delegated click listener and
never wrote the handler branch behind them.** `app.js` has one listener at the
bottom whose `closest()` selector lists every clickable `data-*` attribute. Being
in that list makes a click *reach* the listener. It does not make anything
happen. A rebuild that adds a button to a panel and adds it to the selector, but
stops before the `if (btn.dataset.x)` branch, produces a button that looks
finished, is styled, has a cursor — and silently does nothing.

Nine were found this way. The whole Letters panel was one of them.

**How to check, in one command.** Run this before believing any panel works:

```
node -e '
const s=require("fs").readFileSync("public/devdash/app.js","utf8");
const sel=new Set(); for(const m of s.match(/e\.target\.closest\("([^"]+)"\)/)[1]
  .matchAll(/\[data-([a-z0-9-]+)\]/g)) sel.add(m[1]);
const h=new Set(); for(const m of s.matchAll(/btn\.dataset\.([A-Za-z0-9]+)/g)) h.add(m[1]);
const c=x=>x.replace(/-([a-z0-9])/g,(_,l)=>l.toUpperCase());
const dead=[...sel].filter(x=>!h.has(c(x)));
console.log(dead.length ? "DEAD: "+dead.join(", ") : "no dead buttons");'
```

## 2. Nothing had reached Bloomerang, and could not have

`crm_inbox`: 5 `needs_review`, 2 `rejected`, **0 `pushed`** — ever.

Three writes exist in `crm_write_ledger`, all development, all 15–16 Aug:

| Natural key | Type | Result |
| --- | --- | --- |
| `constituent:14f9…` | constituent | Bloomerang 18803713 → account 4113 |
| `note:new:18803713` | note | Bloomerang 18804737 |
| `attachment:d730…` | attachment | Bloomerang 49, account 165 |

**Root cause.** `gift-scan` stages every donation, sponsorship and grant into
`crm_inbox` and **never sets `match_constituent_id` or `match_method`.** There is
no matching step in it at all — unlike `asks.to_bloomerang`, which calls
`matchConstituent()` and records the result.

So every money row arrived marked "No constituent match", and
`bloomerang.approve` refuses before it does anything:

```
if (payload._accountNumber == null)
  return json({ error: "No constituent matched. Set _accountNumber or create one." }, 400);
```

Verified live on the Micron row — returns exactly that 400 and mutates nothing.

**And the matches exist.** Every queued donor resolves through the canonical
matcher:

| Donor | Card said | `bloomerang.match` returns |
| --- | --- | --- |
| Micron Technology | no match | **3423** (`account_map_name`, 0.65) |
| Jack R. Anderson Foundation | no match | **210** (`account_map_name`, 0.65) |
| Celine Healey | no match | **210** (`sender_map:snapshot`, **1.0**) |
| Victor Hoskins | no match | **2968** (`account_map_name`, 0.65) |

Creating a constituent from that screen would have made a **duplicate of a donor
already on file** — which is how this database came to hold two to four records
for most donors (see §4).

**Fixed in the dashboard**: an unmatched card now looks the match up and shows it.
A confident hit (confirmed sender mapping, or a unique email — score ≥ 0.9) fills
the account number in. A **name-only** hit is offered as "Likely #N · use it" and
is deliberately *not* filled in, because a wrong account number writes a gift
onto the wrong donor's record.

**Fixed in the backend, 28 Aug — `gift-scan` v3.** The scanner now resolves the
donor before it stages the gift, so the match is right in the data and not only
on screen. Two earlier deploys did not land: the function is ~30KB and the upload
came back malformed, so it was **rejected by input validation and nothing was
deployed** — the live scanner was never touched, and the retry was safe. (The
failure mode worth guarding against is the other one: a paste that truncates
*silently* and deploys half a function, which the post-deploy check below
catches. It was run against v3 and the new counters came back live.)

Two details mattered, and both are in the shipped version:

- Mirror the *cheap half* of `bloomerang.matchConstituent` (local tables only —
  `crm_sender_map`, `constituent_clusters`, `crm_account_map`). `bloomerang`'s
  own `requireUser` does **not** accept the service role key, so cron cannot
  call it over HTTP.
- Match on `extraction.donor_email`, **never on the message sender.** The
  Micron grant arrived from `debi@sparcsolutions.org`; matching on the sender
  would file the gift against Debi's own record.

### The patch, as shipped

The full behaviour is written up in `docs/BACKEND.md` under "It resolves the
donor before staging". What follows is the matcher itself, added above
`// ------ the model`:

```ts
const normName = (s: string) => s.toLowerCase().replace(/[^a-z ]/g, "").trim();

async function matchConstituent(email?: string | null, name?: string | null) {
  if (email) {
    const { data } = await db.from("crm_sender_map").select("constituent_id")
      .ilike("email", email).maybeSingle();
    if (data) return { account_number: data.constituent_id, method: "sender_map", score: 1 };
    const { data: m } = await db.from("crm_account_map").select("account_number")
      .ilike("primary_email", email).limit(2);
    if (m?.length === 1) return { account_number: m[0].account_number, method: "account_map_email", score: .95 };
  }
  if (name) {
    const { data: cl } = await db.from("constituent_clusters")
      .select("survivor_account, record_count").eq("norm_name", normName(name)).maybeSingle();
    if (cl) return { account_number: cl.survivor_account,
      method: "cluster_survivor(" + cl.record_count + " records)", score: .7 };
    const { data: n } = await db.from("crm_account_map").select("account_number")
      .ilike("full_name", name).limit(3);
    if (n?.length === 1) return { account_number: n[0].account_number, method: "account_map_name", score: .65 };
    if (n?.length) return { account_number: null, method: "ambiguous_name", score: 0 };
  }
  return { account_number: null, method: "no_match", score: 0 };
}
```

Then in `scan()`, immediately before the `crm_inbox` insert:

```ts
// The donor's email, NOT `from`. See the warning above.
const match = await matchConstituent(ex.donor_email ?? null,
  ex.donor_organization ?? ex.donor_name ?? null);
```

and two fields inside that insert:

```ts
match_constituent_id: match.account_number,
match_method: match.method + (match.score ? " @" + match.score : ""),
```

**Verify after deploying**: fetch the function back and confirm the length is
~30KB and that `ANSWER`-side markers survived — the `SYSTEM` prompt, `classify`,
`enrich`, and the one-gift-per-thread `sibling` lookup. A 30KB upload can
truncate silently; a malformed one is rejected outright and deploys nothing.

**A score of 0.65 is a suggestion, not a match.** If the column is populated
from a name-only hit, the dashboard renders a confident green "Matched" and the
"use it" confirmation is skipped. Either keep name-only hits out of the column,
or teach the card to read `match_method` and treat a `account_map_name` /
`cluster_survivor` match as needing confirmation.

**Backfilled by hand, 27 Aug**: only the one row that resolves at high
confidence — the Jack R. Anderson Foundation grant → account 210, via a
confirmed sender mapping *and* a unique primary email, both agreeing. Account
210's `full_name` is "Jack R. Anderson Foundation" with Celine Healey as its
contact, so the target is right.

The other three were left unmatched **on purpose.** Micron (3423) and Victor
Hoskins (2968) resolve on name alone; writing those into the column would make
the card read a confident green "Matched" and bypass the "use it" confirmation
that exists precisely so a name-only guess cannot file a gift against the wrong
donor.

**One booby-trap worth knowing.** Micron's extracted `donor_email` is
`noreply.grants@benevity.com` — Benevity's no-reply relay, not Micron. It
matches nothing today. If that address ever lands in `crm_sender_map` it will
map every Benevity-routed corporate grant to whichever donor it was first
confirmed against. Do not confirm a sender mapping for a no-reply relay.

## 3b. The letters loop was open — two tables, never joined

`letters.generate` writes **`letter_drafts`**. `donation_ack_status.thanked`
reads **`thank_you_letters`.sent_to_debi_at**:

```sql
LEFT JOIN thank_you_letters l ON l.donation_id = d.id OR donation_fingerprint(...) = ...
... l.sent_to_debi_at IS NOT NULL OR COALESCE(b.acknowledged,false) AS thanked
```

Different tables. So a letter written from the dashboard could never take the
gift off "Owed a thank-you letter", and the same donor would be written to again
and again. `docs/BACKEND.md` recorded this gap on 26 Aug and it was never closed.

A second bug on the same seam: `owedRow` sent `donation_id: g.donation_id`, but
the view exposes the donation as **`id`** — there is no `donation_id` column. So
every letter went off unlinked even where the join would have worked.

**Both fixed.** `generate` and `draft_batch` now also record the letter in
`thank_you_letters`, and the draft to Debi stamps `sent_to_debi_at`.

Two CHECK constraints on that table nearly broke this, and are worth writing
down because neither takes the vocabulary the letters function works in:

| Column | Allowed | Not |
| --- | --- | --- |
| `category` | `General`, `Summit`, `Gala` | a `gift_type` like `gala_sponsorship` |
| `status` | `unsent`, `sent_to_debi`, `mailed` | `letter_drafts`' own `drafted_to_debi` |

Writing the raw values fails the insert outright, which inside `generate`'s
try/catch would have marked every letter `failed` with a 500. Caught by probing
the insert shape against the live table before deploying.

## 9. The chain from a gift to a letter — 27 Aug, later

Erica: "scan my email, give me a draft note for Bloomerang I approve with a
button, and write the thank-you letter automatically." Three pipelines, and the
middle one did not exist.

| Link | State |
| --- | --- |
| Bloomerang → `snap_transactions` | works. 1,676 txns, synced 07:30 daily. |
| email → `crm_inbox` (Bloomerang tab) | works. `gift-scan`, 3×/day. |
| **Bloomerang → the owed list** | **was broken.** See below. |
| owed list → letter → Debi | works (fixed earlier today). |
| `crm_inbox` → the owed list | **no path, by design.** Approving there posts a *note*, not a donation, so an emailed gift never becomes a letter. |

### Why new donations never appeared

`donations_canonical` is a **VIEW**: `donations_staging` where
`status='pending' AND superseded_by IS NULL`. Nothing had written to
`donations_staging` since **14 Aug**. No cron job writes it — the ten scheduled
jobs feed the mirror, the acknowledgements, the account map, the task scan and
the gift scan, and none of them this. It was loaded once and abandoned.

Consequence: **Victor Hoskins gave $25,000 on 18 Aug** — a gala Event Sponsor
gift with 10 tickets, against prior gifts of $10,000 in 2023 and 2024 — and the
dashboard never showed it. Also a $516.83 gala ticket purchase on 20 Aug.

Both are now staged (`source='snapshot'`, `source_id='snap:<txn>'`,
`status='pending'`) and appear in the owed list. Dedupe is by `source_id` **and**
by `donation_fingerprint(donor_name, amount, donation_date)` — without the
fingerprint check a snapshot row duplicates the `bloomerang_form` row for the
same gift. A dry run over all 2026 donations showed every gift back to 11 Aug
correctly recognised as already staged, and exactly these two as new. Five
earlier `source='snapshot'` rows exist from a 14 Aug attempt; all were set
`declined`, so they must be skipped by `source_id`, not re-added.

**Done**: `donation-sync`, deployed and scheduled as cron job
`promote-donations` at **07:45 UTC daily**, right after `bloomerang-snapshot`
loads the mirror at 07:30.

Verified through the cron path itself, not just curl —
`select call_edge_svc('donation-sync', ...)` returned request 152, and
`net._http_response` shows **200** with `ok:true`. That is the check
`## 5` insists on: pg_cron reporting "succeeded" proves nothing.

It never invents a donor. A transaction whose account resolves to no name is
skipped and **reported** under `unnamed`, because `donor_name` is NOT NULL and a
placeholder would flow onto a tax receipt. The fix for those is
`bloomerang sync_accounts`, which is exactly how Virginia Bulger got a name.
